# gem_melee 0.1.0: build specification

Architect's spec for merging GEM MeleeStance 0.7.42 ("stance"), GEM MeleeChase 0.5.4 ("chase") and GEM PenFilter 0.1.1 ("pen") into one
dll, `gem_melee.dll`. Five implementers (WP0-WP4, section 9) build from this file without talking to each other.

- `GM` = `C:\Users\alex_\OneDrive\Desktop\Claude_Indomitus_Project\_tools\gem_melee`. Every path below without a drive is relative to GM.
- Snapshot line numbers: `ms:N` = `inputs\meleestance_0.7.42\src\gem_meleestance.c` (4125 lines, CRLF), `mc/<f>:N` =
  `inputs\meleechase_0.5.4\src\mc\<f>.c` (CRLF), `mcu:N` = `inputs\meleechase_0.5.4\src\gem_meleechase.c` (CRLF), `pf:N` =
  `inputs\penfilter_0.1.1\gem_penfilter.c` (2476 lines, LF), `tp/<f>:N` = `inputs\teleport_0.2.13\src\tp\<f>.c`.
  Every line number in this spec was read in the snapshot; the maps (`design\map_*.md`) hold the background.
- Rule zero: **behaviour parity**. Each module's code stays its snapshot code plus the recorded edits in section 4. The only
  simulation-relevant changes are listed in section 10.2. Anything an implementer thinks needs another change: stop, write it in the
  final report, do not do it.

### 2.2 Semantics of each core service (implementation rules for WP0)
All core locks work before `core_attach_all` (tests call registry / ceasefire / sink without it): SRW locks are `SRWLOCK_INIT` statics;
the sink uses a CRITICAL_SECTION created through `InitOnceExecuteOnce` (recursive, so the crash logger may log from a thread that faults
while holding it).

**Sink** (`core_vlog`): format with `vsnprintf` into a 4096-byte stack buffer; when the result is longer, format again into a

**Clock finder** (core's own, a copy of stance's finder ms:2601-2614): over the exe `.text`, every match of
`8B 9F ?? ?? 00 00 E8 rel32 3B C3 0F 82` whose callee `t` lies in .text with `t[0]==0x8B && t[1]==0x05 && t[6]==0xC3`; the global
`rel32(t+2)` named most often wins; fewer than 5 hits = not found (log, epoch detector then idle, modules keep their own detectors).
Proof obligation: equals stance's / chase's / pen's clock on all three exes (itest `--install` prints all four; parity checks; live
T4 `[link] clock check` line). Expected: game exe+0x1584568, editor exe+0x13DF988, server exe+0x11CBA58 (map_chase 4). The three module
finders differ (ms:2601-2614 getter-reference count, mc/melee:422-431 "dword before QUANT" in eSingleOrder::Tick, pf:627-635 picker
wrapper getter), so equality is also checked at run time: `core_epoch_bind` (3.1 step 7b) attaches a module to the core epoch only when
its clock pointer is the core's.

**New-battle epoch**. The detector reads ONE clock, the core's: `core_epoch_poll` never takes a caller's value, so two time bases can
never mix in its state, and a stale value read before a stall cannot fire it. State `g_state` (LONG64: `(last << 32) | valid`, 0 = no
poll yet), `g_epoch` (LONG), `g_back_ms` = `[Core] NewBattleBackMs` (default 1000, clamp 1..60000), `g_use[CORE_MOD_N]` (1 = attached,
default 1) + `g_det[CORE_MOD_N]` (the value a detached module gets), freeze flag. Lock-free (one compare-and-swap; no lock on the per-pick
path: an uncontended SRW pair would add ~2% to stance's own 2.3 us per call, ms:1879-1883 / live MSlog:1217):
```
uint32_t core_epoch_poll(int mod)
{
    if (frozen) return 0;
    volatile uint32_t *clk = core_clock_ptr();
    if (!clk) return 0;                                            /* no core clock: detector idle, modules run on their own rules */
    for (;;) {
        LONG64 st = g_state;                                       /* state FIRST, then the clock: a successful CAS proves nobody */
        uint32_t now = *clk, last = (uint32_t)((uint64_t)st >> 32); /* moved the state between the two reads */
        LONG64 nx = (LONG64)(((uint64_t)now << 32) | 1);
        if ((st & 1) && now < last && last - now >= g_back_ms) {
            if (InterlockedCompareExchange64(&g_state, nx, st) != st) continue;   /* another thread got there: re-read */
            LONG e = InterlockedIncrement(&g_epoch);               /* only the CAS winner: one fire per back-step */
            if (InterlockedIncrement(&g_lines) <= 200)
                core_log(CORE, "--- new battle %ld: sim clock %u -> %u ms (stance and pen flush at their next detector call)", e, last, now);
            call every listener (fn)(e, now) in registration order;  /* no core lock is held */
            break;
        }
        if (st == nx || InterlockedCompareExchange64(&g_state, nx, st) == st) break;   /* same quant: no write at all */
    }
    return g_use[mod] ? (uint32_t)g_epoch : g_det[mod];
}
```
`core_epoch_bind(mod, clk)`: no core clock -> nothing. `clk == core_clock_ptr()` -> `g_use[mod] = 1`. Else `g_det[mod] = g_epoch;
g_use[mod] = 0;` (frozen at its current value, so a module that already saw it never flushes for it) and one line `[core] WARNING: <mod>
clock exe+0x.. != core clock exe+0x..: <mod> keeps only its own new-battle rule` (a NULL module clock counts as different).
Callers: stance `log_epoch` (ms:2272, S10; it runs from the MatchAmmo hook, the tick and, new, frame_hook at quant start, S3), pen
`epoch_check` (pf:1045, P3; every pen hook, under pen's `g_lock`) and `core_on_quant` (`core_epoch_poll(CORE_MOD_CORE)` at quant start
once stance's quant hook is in). **Chase does not call it and does not OR it in** (10.1 D1): its own rule (mc/melee:639-665) already
catches every backward step of its clock, and chase is the one module whose code may run on MP clients (its comment at mc/melee:639-643
relies on every machine resetting on the same quant; whether vs_tick runs on clients is not traced), while the core's polls are machine
dependent (core_on_quant needs the quant hook, the stance / pen hooks run only where picks run, ms:1737-1740). Stance and pen OR in "core
epoch changed since I last looked" (S10 / P3), skip that term on their own first call (nothing of an earlier battle is held then) and
log one `flush for core new battle %u (own rule did not fire)` line before their unchanged flush line when only the core term fired.
Listeners (link only) run on the detecting thread, must not call into any module and may take only their own leaf lock (the poll can run
inside pen's `g_lock` or inside stance's hook).

**Patch registry** (`core_patch_*`). Table of `CORE_PATCH_MAX` entries under an SRW lock. For a call:
1. `len` 1..32 (ptr: 8) else REFUSED_FULL; table full -> REFUSED_FULL.
2. Overlap: `[addr, addr+len)` intersects any WRITTEN entry (any module) -> REFUSED_OVERLAP.
3. Current bytes copied to `orig`; `expected != NULL` and `memcmp(addr, expected, len)` differs -> REFUSED_BYTES (nothing written).
   For ptr writes `expected` is the expected pointer VALUE (compare `*slot == expected`).
4. Write. CODE: `VirtualProtect(addr, len, PAGE_EXECUTE_READWRITE)`; when `[Core] PatchSuspendThreads=1` (default) suspend every other
   thread of the process with the logic of mc/patch:37-62 (snapshot, retry up to 20 x with Sleep(5) while a thread's RIP is inside
   `[addr, addr+len)`, more than 1024 threads or no snapshot = FAILED, nothing written); `memcpy`; resume; restore protection;
   `FlushInstructionCache`. DATA: `VirtualProtect(PAGE_READWRITE)`, memcpy, restore (no suspension). PTR: `VirtualProtect(slot, 8,
   PAGE_READWRITE)`, `*old = *slot` (when old != NULL), `*slot = value`, restore (no suspension; an aligned 8-byte store).
   VirtualProtect failure = FAILED.
   **Attach batch** (STARTUP_batch, review INST-1, Nov 21 2026; `core_patch_batch_begin()` / `core_patch_batch_end()`, core_int.h).
   One Toolhelp thread snapshot costs about 6 ms + 37-41 ms on a PC with ~5900 system threads; the 13 code writes of an attach (chase
   6, stance 1, pen 6) took ~0.55 s of every start that way (the three old dlls ~0.25 s: only chase suspended), and the launcher gives
   the payload chain a limited number of 100 ms rounds. Inside DllMain the loader lock is held, so a thread created during the attach
   runs no user code before DllMain returns: the set of threads that can execute is fixed for the whole attach and ONE walk serves
   every code write. core_attach_all opens the batch around the three module attaches of the REAL attach (3.1). Inside a batch the
   first CODE write that suspends takes the snapshot once and keeps the other threads' handles (`OpenThread(THREAD_SUSPEND_RESUME |
   THREAD_GET_CONTEXT)`); every CODE write of the batch then only runs SuspendThread / GetThreadContext (the same "a thread
   executes inside [addr, addr+len)" test and bounded retry: up to 20 attempts, all resumed and Sleep(5) between) / ResumeThread on
   those handles; batch_end closes them. A thread that has exited (SuspendThread fails) is skipped and never resumed. No snapshot, or
   more than 1024 other threads: that write is FAILED exactly as without the batch, and the batch's next write walks again (as each
   write did). Only writes from the thread that opened the batch use it; another thread's write takes the normal path (the kept
   handles hold neither that thread nor the opener). Outside a batch nothing changes: one walk per write (stance's lazy H2 is a PTR
   write and never suspends; any later code write keeps this path). `[Core] PatchSuspendThreads=0` = never suspend, batch or not.
   Nothing is logged, allocated or locked between suspend and resume (the registry's SRW lock is taken before, as always). After
   `core_patch_report()` core_attach_all logs one line from the counters (`core_patch_suspend_stats`): `code writes: 13 with the other
   threads suspended, 1 thread walk (attach batch, N other threads), X ms` (the itest's dry run: `13 thread walks (one per write, no
   attach batch, up to N other threads)`; `, F FAILED (the other threads could not be stopped safely)` when writes failed for it; `,
   E exited during the batch`; no code write: `code writes: none (attach batch open, no thread walk needed)`; PatchSuspendThreads=0:
   `code writes: N, the other threads not suspended ([Core] PatchSuspendThreads=0)`). Results, states and the report text are
   unchanged.
5. Record `now` bytes, state; log one line on refusal / failure immediately (`[core] patch REFUSED (overlap with <mod> <name>
   exe+0x..): <mod> <name> exe+0x.. <len> bytes`, `... REFUSED (bytes differ: expected <hex> found <hex>)`, `... FAILED (<reason>)`);
   return value: 1 for WRITTEN, 0 for every other state (never the state code: the callers test `!core_patch_*(...)`, S4 / S13,
   C7-C10 via mc/melee:1047-1060, P8 via pf:1831 / 1848 / 1865 / 1883).
The registry never builds stubs or jumps: every module hands it the exact bytes it writes today (stance's `FF 25` jump straight to
`ms_hook` stays a jump, so `__builtin_return_address(0)` in ms_hook stays the engine call site, ms:1972/1984). `core_patch_report()`
logs `patches: N written, M refused/failed` and one line per entry:
`  #%02d %-6s %-28s exe+0x%llX %2u bytes %s -> %s %s` (orig hex, new hex, state). Runtime writes (stance H2) are logged as they happen.
Partial installs are NOT rolled back (as today in all three: map_chase 10.9, map_pen 10.17); the refused write's own module takes its
existing failure path.

**Background thread**: started once at the end of `core_attach_all(dry=0)` (CreateThread; never waited on). Loop: `Sleep(100)`, call

## 6. Integration rules (src\link\link.c, WP4)

`link_attach(sc, ss, sp)` runs in this order (the module hooks are already live, and in the server late-load path an engine thread can
pick at any moment): (1) read `[Link]` keys and the five word keys; (2) zero every link table and `core_suspect[]` (statics, already
zero; the SRW lock is `SRWLOCK_INIT`, nothing to create); (3) take the read-only module answers it needs once: `chase_layout`,
`chase_enttags_off()` (else `stance_enttags_off()`) for the tag offset, `stance_name_vec_off()`; (4) `core_set_link_hooks`;
(5) `core_epoch_listen(link_on_new_battle)` and `core_bg_register(CORE_MOD_LINK, link_bg_step)`; (6) `MemoryBarrier()`; (7) set
`core_trace_on = Trace`, `core_timing_on = CostLine && [MeleeStance] HookTiming`, `core_flip_on = Flip` (the switches last); (8) log R1,
R6 and the cross-checks.

Link rules (CS-B / CS-4): link never calls into a module except the read-only APIs of 2.1. All link tables are log-only, fixed-size and
direct-mapped (1024 entries, slot `core_suspect_slot(unit)`), keyed by (entity pointer, entity id read at note time from the live
unit, e+0xC0); a slot whose key differs is overwritten, never searched linearly. One SRW lock (a leaf lock: never held while calling
anything outside link) guards them; it is taken only inside the note / trace hooks, which run for suspects, front-order changes and
traced units only, never on an ordinary pick. Every name link keeps is COPIED into a fixed char array at note time with
`core_vec_names` (no engine `char *` is kept); stored unit / ammo / target pointers are only printed, never dereferenced after the note
call returns. NULL ammo, NULL `ti` (ctx+0x10), NULL target and NULL weapon item mean "none". The flip block is built and written inside
the note call that trips it, on the calling (engine) thread, while that unit is live; `link_bg_step` only writes the cost line (counters,
no unit pointers). Offsets come from the modules (step 3), not from constants.
